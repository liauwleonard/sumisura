# Decisions — sumisura

Newest first. Each entry: what was decided, why, and what was rejected.

---

## 2026-08-16 — The cloud is optional, and sign-ups are invite-only

### Unconfigured means local-only, never broken
If `VITE_SUPABASE_*` are absent the app skips auth entirely and runs exactly as it did in
Phase 2. Two reasons: the published site must keep working in the window between auth shipping
and secrets being added to CI, and a tailor must never be locked out of measurements he already
took because a config value went missing. Rejected: failing hard on missing config, which is
tidier for a developer and hostile to the person actually using the app.

### Invite-only sign-ups
`shouldCreateUser: false`, with accounts created from the Supabase dashboard. The anon key is
public by design, and with open sign-ups anyone scraping GitHub could register accounts and
exhaust the free tier's email quota. For a one- or two-person shop, an invite is no burden.

### Magic link, no passwords
A tailor should not have a password to forget, and password reset is just email login with
extra steps. Trade-off: login depends on him receiving email on the device — confirmed
acceptable before building.

### Timestamps stay epoch milliseconds in Postgres
`bigint`, matching the local Dexie records exactly, rather than `timestamptz`. The cloud copy
is a mirror, not a second source of truth; one representation of "when" removes a whole class
of timezone conversion bugs at sync time.

### The change log is append-only in the database
`change_log` has select and insert policies and deliberately no update or delete policy. An
audit trail that can be quietly rewritten is not an audit trail.

## 2026-08-16 — English default; preferences persist only on explicit choice

Default language switched from Bahasa to English at Leonard's request. Bahasa remains one toggle
away in Settings and every string is still translated.

The more interesting half: preferences used to be written to localStorage by an effect on mount,
so the shipped default was captured on a user's very first load. That makes the default
permanently unchangeable for anyone who has already opened the app — a later change would reach
new installs only. Now `setLang`/`setUnit` write on an explicit choice and nothing else, so the
default stays live until the user actually picks something.

## 2026-08-16 — Named Sumisura

*Su misura* is the Italian trade term for made-to-measure — it already carries both halves of what
the app is: the measurement and the fact that it is custom. Closing it into one word turns a real
phrase into a brand rather than inventing a word from nothing.

Rejected: Indonesian names (*Meteran*, *Buku Ukur*) — Leonard preferred a classic foreign language;
*Sartoria* (names the shop, not the work); *Custura*, a coined CUSTom + misURA blend that happened
to land near *costura* (sewing, ES/PT) — good, but invented where an authentic term existed.

The rename touched the Vite `base`, the manifest, and the **IndexedDB database name**. Done before
the app has real users, so no migration was needed — doing it after the tailor starts working would
have meant writing one.

## 2026-08-16 — Phase 2 decisions

### Update prompt, not `autoUpdate`
`vite-plugin-pwa`'s `autoUpdate` reloads the page when a new service worker takes control.
Saving in this app is explicit, so a reload could land mid-measurement and throw away numbers
the tailor just took off a customer. `registerType: 'prompt'` shows a dismissible card instead.
Costs one small component; removes a whole class of data loss.

### Icons generated by a script, not a dependency
`scripts/make-icons.mjs` writes the PNGs with a hand-rolled encoder (zlib + CRC32, distance-field
shapes). Rejected: adding `sharp` or `@vite-pwa/assets-generator` — native modules that would need
to install in CI for a four-file, three-shape icon. Edit `public/icon.svg`, mirror the change in
the script's constants, re-run it.

### iOS needs its own meta tags
Safari does not use the web manifest to decide install behaviour, so `apple-mobile-web-app-capable`,
`apple-mobile-web-app-title` and `apple-touch-icon` are declared in `index.html` separately. All
three of the tailor's devices are Apple, so getting this wrong would have broken the whole point.

### Repo must be public
GitHub Pages on a free account only serves from public repositories. That is acceptable here: the
repo holds application code only. Customer data lives in the browser (and, from Phase 3, in
Supabase behind row-level security) — never in git.

## 2026-08-15 — Payment state is derived, completion state is stored

Two indicators, deliberately asymmetric:

- **Completion status** is a stored field the tailor sets directly, so it gets a dropdown on the
  orders list. He marks things Ready or Collected constantly and should not have to open an order
  four screens deep to do it.
- **Payment status** is computed from price vs payments every time it is read. There is no field to
  set, which is precisely why it can only change from Order → Balance — you move it by recording
  money, not by picking a label. Rejected: storing a payment status field, which would let the
  label drift out of sync with the actual numbers.

An order with no price shows "Not priced" rather than "Unpaid" — claiming a customer hasn't paid
when nobody has quoted them yet is wrong.

### Payment references are logged, not just stored
`Payment.ref` holds the transfer or receipt number. The change log records a payment summary
(`2000000 (BCA/TRF/20260815/7781)`) rather than a running total, because a reference number that
can be silently edited is useless for reconciliation.

## 2026-08-15 — Phase 1 build decisions

### Measurement fields come from standard suit-tailoring practice
Leonard's tailor measures on the body and writes freehand notes ("arms = 50cm"), so there was no
existing vocabulary to copy. Built the standard set and made it cheap to correct: every label is
an i18n key, so renaming or reordering is a dictionary edit that never touches stored data.
Rejected: blocking the build until a notebook page could be photographed.

### Saving is explicit, not per keystroke
The Save button plus an automatic save when switching steps. Autosaving on every keystroke would
fill the change log with `9 → 96 → 98` instead of one clean `98 → 100`. Step-change saves keep a
long measuring session from being lost.

### Order-level measurement snapshot, not a customer-level record
The order holds its own frozen copy; prefill reads backwards through the customer's previous
orders at the field level. Keeps history honest without a separate versioning table.

### Bilingual and cm/inch pulled forward from Phase 4
Not scope creep: labels had to live in a dictionary anyway for the renaming point above, and once
that exists the second language is data entry. The unit toggle is three lines given canonical cm
storage.

### Mannequin viewBox has label gutters
`-130 0 660 620` with the body at x 40–360. Found during verification — Indonesian labels
("Lingkar lengan atas", "Panjang celana luar") clipped off the left edge of a body-tight viewBox.

## 2026-08-15 — Kickoff: architecture and scope

**Context.** A working tailor (suits, custom + alterations, ~20 active customers, solo but may add
an assistant) currently uses a paper notebook and mixes up which notes belong to which client. He
works across an iPad, a MacBook, and a phone. The app may later be shared with other tailors.

### Hosting: GitHub Pages + PWA
Static hosting is free and sufficient. A PWA installs on iPad/Mac/iPhone with its own icon and
works offline. Rejected: native apps (cost, App Store friction, three platforms).

### Sync: Supabase, local-first
App reads and writes IndexedDB always; sync runs in the background. Shop wifi dropping must never
block work.

Rejected:
- **Firebase** — Firestore's offline sync is excellent, but Cloud Storage now requires a billing
  account. Moot once photos were cut, but Supabase's Postgres is easier to reason about and export.
- **Cloudflare D1 + R2** — cheapest and no idle-pause, but we'd write auth and sync from scratch.
- **CloudKit** — native fit for three Apple devices, but needs a $99/yr developer account.
- **No sync at all** — was the initial recommendation; overridden because he genuinely uses three
  devices.

Accepted risk: Supabase free projects pause after ~7 days idle. Daily shop use means this never
fires.

### Privacy: Row Level Security, not encryption
Every row carries `shop_id`; the database enforces "you may only touch your own shop's rows",
server-side, so it can't be bypassed from the client. The Supabase anon key is public by design.

**Known limit:** the project owner (Leonard) can read any user's rows from the Supabase dashboard.
Considered end-to-end encryption to close this; **rejected** — tailor measurements aren't sensitive
enough to justify the complexity, and a forgotten password would destroy data permanently with no
recovery path.

### `shop_id` scoping from day 1
He's solo now but is considering an assistant. Scoping by shop rather than by user costs almost
nothing today and turns "add an assistant" into a rule change rather than a migration.

### Order-centric flow with a customer record underneath
He thinks in pages: a new order is a new page. The UI honours that — the flow is
Login → Order → Measurement → Material + Cut Style → Balance.

But step 1 is **search-or-create**, not free text. Typing a name surfaces existing customers; phone
number is the hard dedup check. Without this the app would recreate the notebook's core failure
(three "Pak Budi" entries) in software.

### Measurements: snapshot per order + full change log
Each order freezes its own measurement set. Edits are always allowed but never silent — every
change writes `field, old, new, timestamp, who, optional reason`. An order cut in March still shows
March's numbers after a September re-measure.

Rejected: a single mutable measurement record per customer. It loses the history that makes the app
better than the notebook.

### Prefill from the latest order
Carries over: customer details, measurements, cut style. Does not carry over: material, balance.
Field-level fallback fills any gap from the most recent order that had that field, so a
measurements-light alteration never leaves a half-empty form. Prefilled values are tagged
`from order #N · date` until edited, plus a "Measure fresh" button.

### Customers are records, not accounts
Only tailors authenticate (magic link — no password to forget). Customers never log in, get no
portal, and receive no automated messages. Rejected: customer sign-up, SMS/WhatsApp automation.

### Photos cut entirely
Originally planned customer face photos and fabric photos. **Removed at Leonard's direction** —
measurements and notes only. This also removes the storage-quota and image-compression concerns.

### Stack: Vite + React + TypeScript + Dexie + Tailwind
Forms and cross-field state (mannequin ↔ inputs) get messy in vanilla JS. TypeScript catches
measurement-field typos, which are the most likely silent bug in a project like this. Leonard also
wants to build his coding skill, and TS teaches more than it costs here.

### Money stays dumb
Total, deposits, auto-computed receivable, status. No invoices, tax, or reports. Pay-on-order is
the norm; deposits are the exception worth tracking.

### Build order: local → PWA → sync → polish
Phases 1–2 put a working tool in his hands before the risky sync work begins. The data model should
survive contact with reality before it's mirrored to a server.
